# Languages

[← docs index](README.md)

The site ships the catalogues `MESSAGES` imports, at the top of
`profile.config.ts`. **That map is the whole locale setup** — no source file
keeps a second copy of the list.

```ts
import en from "./src/i18n/messages/en";
import ru from "./src/i18n/messages/ru";

export const MESSAGES = { en, ru };   // English-only? delete the ru line.
```

The first entry is where the language toggle starts; `terminal.defaultLocale`
picks which one is served unprefixed. With one locale configured the toggle and
the `lang` command disappear, and `/cv.html` has no `/<locale>/` sibling.

## How the locale set is derived

`src/i18n/locales.ts` reads the map and nothing else:

```ts
export type Locale = keyof typeof MESSAGES;
export const LOCALES = Object.keys(MESSAGES) as Locale[];
export type Localized<T = string> = Record<Locale, T>;
```

Because `Localized` is `Record<Locale, T>`, adding a language makes TypeScript
name every `profile.config.ts` field that still needs translating — one error per
field. A half-translated site can't build.

`terminal.defaultLocale` is typed `Locale`, so naming a language you don't ship
is a compile error too.

## What ships

`src/i18n/messages/` carries thirteen catalogues. Every one is translated from
`en.ts`, typed against it, and held to the same tests whether or not a site
selects it.

| code | language | note |
|---|---|---|
| `en` | English | the schema every other catalogue is typed against |
| `ru` | Russian | |
| `uk` | Ukrainian | |
| `es` | Spanish | |
| `pt` | Portuguese | **Brazilian** Portuguese |
| `fr` | French | |
| `it` | Italian | |
| `de` | German | |
| `pl` | Polish | |
| `tr` | Turkish | |
| `zh` | Chinese | **Simplified** Chinese; renders in the system font |
| `ja` | Japanese | renders in the system font |
| `ko` | Korean | renders in the system font |

*Renders in the system font*: JetBrains Mono has no CJK glyphs, so those
strings fall back to the visitor's monospace font. Readable everywhere, a
different face from the Latin UI; the ASCII art is unaffected. The plain
two-letter codes are deliberate — `pt-BR`-style tags would put quoted keys in
every `Localized` field of a fork's config.

Jokes were adapted rather than translated: puns get a native equivalent where
one exists, while Kubernetes statuses, the Terraform/sudo/bash parodies, the
`[  OK  ]`/`[FAILED]` dmesg tags and the leet fingerprint stay as they are, so
the output still reads as terminal output.

## Dropping a language takes its translations out of the build

This site selects two of the thirteen, so the other eleven sit in the repo and
**never reach `dist/`** — a test asserts exactly that.

It matters because each catalogue is roughly a fifth of the JavaScript a visitor
downloads. `ru.ts` is 7.8 kB gzipped against a 37 kB bundle.

Removing a language works in reverse to adding one: TypeScript names every field
still carrying its prose, so dead translations can't linger in the config.

## Adding a language

1. A new file in `src/i18n/messages/` typed as `Messages`
2. Its import and entry in `MESSAGES`

`en.ts` is the schema — `Messages = typeof en` — so every catalogue is checked
against it. That import is type-only and erased at build, so it costs nothing
even in a fork that doesn't ship English.

`npm test` covers what types can't see: placeholder parity, scripted-sequence
lengths, inline markup (`<span class="…">` and entities have to match `en`
leaf for leaf), and that `lang.set` names the language in itself — **across
every catalogue on disk** rather than only the selected ones. An unselected
catalogue is one import away from being live, so it's held to the same standard.

## Why locales.ts imports from the config

It looks backwards. It works because `src/core/profile.ts` imports `Localized`
and `Locale` with `import type`, which is erased at build — so
`locales.ts → profile.config.ts → core/profile.ts` is a types-only cycle that
never exists at runtime.

`MESSAGES` is a separate export rather than a field on the profile for the same
reason: nested, its type would depend on `ProfileConfig`, which depends on
`Locale`, which would depend on it.
